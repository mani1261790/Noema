# Noema UIスタイルガイド

ステータス: 現行MVP基準

基準: デジタル庁デザインシステムβ版 v2.16.0

## 1. 適用方針

Noemaの公開ブログと執筆エディターは、デジタル庁デザインシステムの基本デザイン、コンポーネント、アクセシビリティガイドラインをUIの基準として使う。

これはデジタル庁ウェブサイトのブランド、ロゴ、文章、ページ構成を複製するという意味ではない。デジタル庁デザインシステムは個々のサービス用スタイルガイドへ再定義して使うプラットフォーム型デザインシステムであるため、Noemaの情報設計とブランドをこの文書で追加する。

### 1.1 適合レベル

ブログUIは、固定したデジタル庁デザインシステムβ版 v2.16.0のうち、Noemaの画面とコンテンツに適用可能なすべての規範、仕様、アクセシビリティ要件へ適合させる。単に色や余白を似せるのではなく、情報構造、状態、操作、レスポンシブ挙動、支援技術向けの意味まで含めて適合対象とする。

- 公式コンポーネントが存在する用途では、その仕様とコードスニペットを優先する
- 公式デザイントークンを使い、根拠のない色、文字サイズ、余白、角丸、影を追加しない
- コンポーネントの見た目だけを流用して、定められた意味や操作方法を変更しない
- コンポーネントの形状と操作はDADSに従い、ブランドと記事分類にはNoemaのカラートークンを適用する
- DADSにない固有のコンポーネント構造は、記事アシスタントの質問カードだけとする
- 独自拡張には、必要な理由、参照した公式規範、アクセシビリティ検証結果を記録する
- 既知の不適合を残した状態を「準拠」と呼ばない

固定版の更新は自動追従させない。新しい公式版との差分を確認し、Noemaの対応表、実装、テストを同じ変更単位で更新する。

## 2. デザイン原則

### 内容を先にする

装飾より、見出し、本文、図、出典の順序と可読性を優先する。記事一覧カードの見栄えのために本文や要約を不自然に切らない。

### 専門性を隠さず、入口をやさしくする

専門用語を消すのではなく、最初に日常語で意味を説明し、正式名称へ接続する。読者へ順路や現在地を示すのではなく、記事そのものの面白さから入れる見出しと要約を使う。

### 操作を予測可能にする

リンクはリンク、ボタンは動作として表現する。公式カードのように全体をリンクにする場合はリンクを1つだけ置き、入れ子のリンクや競合する操作を避ける。ホバーしないと分からない情報は置かない。

### AIを本文より強く見せない

記事アシスタントは補助機能であり、記事本文、著者、出典と視覚的に区別する。AI回答を記事本文の一部に見せない。

### アクセシビリティを完了条件にする

キーボード操作、フォーカス表示、意味のある見出し階層、代替テキスト、拡大表示、コントラストを実装後の追加作業にしない。

## 3. 基本デザイン

### タイポグラフィ

- 日本語本文とUI: `Noto Sans JP`
- コード: `Noto Sans Mono`
- 公開ブログとStudioはDADSの定義済みテキストスタイルだけを使用し、中間値や流動的な`clamp()`で文字サイズを作らない
- デジタル庁ホームページの記事CSSと同じ対応として、ページ・記事の`h1`はモバイル28px / デスクトップ45px、記事本文の`h2`は24px / 32px、`h3`は22px / 28pxとする
- 通常本文は17px・行高170%、通常UIは16px以上、補助表示はDense 14pxを使用する
- 各サイズではDADSが定義する太さ、行高、字間を必ずセットで適用する
- 本文の行長: デスクトップで概ね45〜80文字に収める
- 本文の行間: 長文を読み続けられる値を優先する
- 見出しレベルを見た目だけで飛ばさない
- 数式やコードより先に、平易な説明を置く
- 記事本文の見出しには、左線、チップ、飾り罫、下線その他の独自装飾を付けない

### カラー

- Noemaのキーカラーは、思考の落ち着きと技術への入口を表す深い青緑`#00645F`とする
- 背景は紙に近い`#FAF9F5`、本文は青緑をわずかに含む墨色`#1C2422`、カード等のサーフェスは白とする
- キーカラーのhoverは`#004F4B`、activeは`#003C39`とし、状態が深い色へ一貫して移るようにする
- 記事タイプには、体験`#9A4B00`、活用`#00645F`、開発`#4355A5`、理論`#7A3E87`を使う
- 体験・活用・開発・理論の色は序列ではなく同格の記事タイプ色として扱い、公開UIに記事タイプ名やLevelを表示しない
- focusの黄、エラーの赤、成功の緑など、意味が定着している機能色・セマンティックカラーはブランド色へ置き換えない
- 文字はサイズにかかわらず背景とのコントラスト比4.5:1以上を基準とする
- 枠やアイコンなどの非テキスト要素は隣接色とのコントラスト比3:1以上を基準とする
- 状態、記事の位置付け、エラーを色だけで伝えない
- リンクは本文色と区別し、下線または同等の非色情報を持たせる

### レイアウト

- 1カラムの本文を基本にし、補助ナビゲーションは本文の幅を圧迫しない
- デスクトップでは本文、目次、補助パネルを必要に応じて配置する
- モバイルでは本文を最優先し、目次とチャットは折りたたむ
- 固定ヘッダーや固定チャットが小さい画面を覆わないようにする
- 200%拡大と幅320 CSS px相当でも横スクロールなしで本文を読めることを目標とする

### 余白と形状

- 余白は公式スケールを使い、任意値を増やさない
- カード、入力、ボタンの角丸はNoema内で一貫させる
- 影は階層や前後関係を示す場合だけ使う

## 4. 使用する主要コンポーネント

| Noemaの用途 | デジタル庁デザインシステムの基準 |
| --- | --- |
| サイトヘッダー | デジタル庁ホームページのヘッダー適用例。現行はブランドと検索だけを置く |
| 現在位置 | パンくずリスト |
| 記事タイトルと節 | 見出し |
| 記事一覧 | カード、チップラベル |
| 長文ナビゲーション | 目次、スクロールトップボタン |
| 補足・注意 | 注釈ブロック、ノティフィケーションバナー |
| 参考情報の開閉 | ディスクロージャー。本文の必須情報には使わない |
| 一覧移動 | ページナビゲーション |
| 検索 | 検索ボックス |
| APIキー・質問入力 | インプットテキスト、テキストエリア、ボタン |
| モバイルのチャット | ドロワー、ハンバーガーメニューボタンとは役割を分離 |
| 処理中 | プログレスインジケーター |
| LLM/APIエラー | ノティフィケーションバナー |

カルーセル、メガメニュー、モーダルダイアログは、情報設計上必要であることを説明できる場合だけ使う。

## 5. 画面別ルール

### トップページ

- ヒーローはNoemaのブランドメッセージだけを表示し、特定記事のタイトル、要約、記事リンクを置かない
- ヒーローはDADSの`Dsp-48B-140`、`Std-17N-170`、1カラムのリキッドレイアウト、既存余白スケールで構成する
- 最初の画面で「専門技術を、専門外の人にもわかる言葉で説明する」サイトだと伝える
- シリーズを主要な入口とし、まとまりの説明と公開中の記事順を伝える
- 記事カードの分類名は公開せず、テーマ、タイトル、要約で内容を伝える
- カードの枠は四辺を同じ幅にし、左辺だけの線を使わない
- 記事カードは1pxの四辺外周、12px角丸、タイトル下線、hover・focus状態を一貫して使う
- 四辺の枠とタイトル下線にはNoemaのキーカラーを使い、左辺だけの線や分類色の面塗りは使わない
- シリーズと新着記事から記事へ入り、検索へ移動できるようにする
- 導入部には記事CTAを置かない。Noemaの考え方を示すブランドイラストは、本文コピーを置き換えず、装飾画像として扱う場合に限り配置できる
- OIFの名称や勧誘CTAを主要導線へ置かない

### 記事一覧

- タイトル、要約、テーマ、日付を表示する
- カード内に複数の競合するリンクを置かない
- キーワード検索を主操作として常に表示し、シリーズ、テーマ、タグはDADSのディスクロージャー内に詳細条件として配置する
- 検索入力にはラベルとサポートテキストを用意し、プレースホルダーだけで用途を説明しない
- 0件時に検索条件を解除できる導線を出す

### ヘッダー検索

- 専用検索ページは設けず、ヘッダーの検索ボタンからDADSの検索ボックスを展開する
- 展開内は虫眼鏡の送信ボタンと下線付き入力だけのNoema向け最小構成とし、記事一覧の大きな検索ボックスを複製しない
- 開閉状態を`aria-expanded`で伝え、展開時は検索入力へ、Escapeで閉じた時は開閉ボタンへフォーカスを移す
- 開閉のモーションは短い`ease-out`とし、`prefers-reduced-motion`では無効化する
- 検索結果は記事一覧へ引き継ぎ、キーワード、シリーズ、テーマ、タグの条件をURLで共有できるようにする

### 記事ページ

- `h1`は記事タイトル1つだけにする
- 記事本文の見出しはデジタル庁ホームページと同じ無装飾の見出しとし、DADSの文字サイズ・行高・字間だけで階層を示す
- 目次は見出し構造から生成する
- 図には代替テキストまたは本文中の同等説明を用意する
- 図解は深い青緑の線、紙色の背景、記事タイプ色の補助点を基本とし、発光、ロボット、脳、回路基板をAIの記号として安易に使わない
- 記事一覧とシリーズ一覧は、タイトルと説明を比較しやすいテキスト中心の表示を維持する
- コードブロックは横スクロール可能にし、ページ全体をはみ出させない
- 外部情報には出典と最終確認日を示せる構造を持つ

### 記事アシスタント

- APIキー入力前に保存しないことと送信先を説明する
- パスワード型入力と表示切替を用意する
- 送信中、成功、上流APIエラー、キー不正、制限超過を区別する
- 回答には「AIによる回答」と根拠見出しを表示する
- 会話を消去する操作を用意する
- チャットを使わなくても記事の全情報へアクセスできるようにする

### 執筆エディター

- 画面幅にかかわらず本文、プレビュー、設定を1ペインずつ表示し、利用者が同時に扱う作業対象を1つに絞る
- 本文、プレビュー、設定のどれが選択中かを明示する
- CMSへの保存状態、検証エラー、レビュー状態、公開状態を色とテキストで示す
- レビュー状態と公開状態を混同せず、現在のrevisionと公開中のrevisionが異なる場合は文章で説明する
- 利用者のroleと、そのroleで実行できる操作を表示する
- 検証エラーから該当frontmatterまたは本文位置へ移動できるようにする
- レビュー依頼、承認、修正依頼、公開、保管は、破壊的でない編集・保存操作と視覚的に分ける
- 保存競合では入力内容を保持し、エディター直下でブラウザ原稿とCMS最新版のrevision、更新者、更新時刻を示す。全文採用、Markdown書き出し、記事情報の項目別・本文の変更ブロック別統合を選べるようにする
- `localStorage`は復旧コピーであり、CMS保存や共有の完了を意味しないことを示す
- 限定URLは認証ではないこと、指定メンバー公開は現在利用できないことを公開範囲の選択肢内で説明する
- R2が未有効の間は画像uploadが利用可能に見える操作を表示しない

## 6. アクセシビリティ受入条件

- WCAG 2.2 AAを目標とする
- 主要フローをキーボードだけで完了できる
- フォーカス位置が常に視認できる
- スクリーンリーダーでランドマーク、見出し、フォーム名が解釈できる
- エラーは該当入力と関連付け、修正方法を文章で示す
- 動きは `prefers-reduced-motion` を尊重する
- タッチ対象は誤操作しにくいサイズと間隔を持つ
- 自動アクセシビリティテストに加え、記事閲覧とチャットを手動確認する

## 7. 適合性の検証

実装PRでは、画面やコンポーネントごとに次の対応表を更新する。

| 項目 | 記録内容 |
| --- | --- |
| Noemaの画面・部品 | 対象のURL、コンポーネント名、状態 |
| 公式参照 | v2.16.0の基本デザインまたはコンポーネント文書 |
| 実装元 | 公式HTML/Reactコードスニペットのcommit、または独自実装の理由 |
| 自動検証 | axe、HTML構造、コントラスト、レスポンシブ、ビジュアル差分 |
| 手動検証 | キーボード、スクリーンリーダー、拡大、モバイル操作 |
| 結果 | 適合、不適合、非該当とその根拠 |

最低限、CIとレビューで次を確認する。

1. lint、型検査、ビルド
2. 主要画面に対する自動アクセシビリティ検査
3. 320 CSS px相当、200%拡大、デスクトップ幅のレイアウト検査
4. キーボードだけで記事閲覧、検索、APIキー入力、質問、会話消去ができること
5. フォーカス、hover、active、disabled、loading、errorを含む状態のビジュアル差分
6. 見出し、ランドマーク、フォームラベル、エラー関連付けの手動確認
7. デジタル庁デザインシステム対応表に未確認項目がないこと

ブログUIの完成条件は、適用可能な公式規範に対する既知の不適合が0件であり、上記の証跡がレビューされていることとする。
